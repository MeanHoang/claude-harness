# Analyze Task — Notion Spec Intake & Verification

Turn a BA-written (AI-generated) Notion spec into **verified, decision-complete requirements** with ONE round of questions — so the user answers once and coding can proceed without further back-and-forth.

**Core rule** (from team experience): Notion specs are AI-generated by BAs. **Trust only the GOAL.** Every field name, file reference, behavior claim, and analysis statement must be verified in code before believing it.

## Inputs

- A Notion task URL or page ID (fetch via `notion-tasks` skill), OR
- A pasted spec / task description (skip fetch, same analysis).

## Workflow

### Step 1: Fetch the task

```bash
python3 .claude/skills/notion-tasks/scripts/notion-tasks.py get <page_id_or_url>
```

Read the full body AND comments (comments often override the body — later decisions live there).

### Step 2: Split GOAL vs CLAIMS

- **GOAL** — what the merchant/user should be able to do. Trust this.
- **CLAIMS** — everything that asserts how the system currently works or should be built: field names, collection names, file paths, "X already supports Y", API shapes, UI surface names. Do NOT trust any of these yet.

### Step 3: Verify every claim in code

For each claim, find evidence (Grep/Read, or Explore agent for broad sweeps):

| Verify | How |
|---|---|
| Field/collection exists? | grep repositories/, functions.d.ts, firestore-indexes/ |
| Behavior claim ("X already does Y") | read the actual service/handler code |
| Which surface is LIVE? | check extension entry points vs legacy scripttag — legacy thank-you page is dead; reward-celebration UI ext is live |
| Does BE already compute the value? | check existing services before planning new computation (e.g. calcPointService already had calcStoreCredit) |
| FE can see the field? | check `pickFields.js` whitelist — unlisted shop fields are silently undefined |

Build a claim table: **claim → verdict (✅ đúng / ❌ sai / ⚠️ không tìm thấy) → evidence `file:line`**.

### Step 4: Gather the numbers (data-driven)

For each decision the spec leaves open, get the real figure that informs it:

- Is the feature/field **already in use**? → query Firestore/BigQuery for shop counts, or grep for existing writes.
- Rollout risk → how many existing shops are affected (the product may have thousands of active tenants — every change must cover them: grandfather / feature gate / migration).
- Cost-relevant choices (new query, new index, bulk op) → estimate reads/writes; check `firestore-indexes/` for an existing index.

Never present a decision without its number when the number is obtainable.

### Step 5: Classify open points

0. **Goal confusion** — the GOAL itself is unclear, self-contradictory, or doesn't make sense against how the system actually works. Say so plainly ("chỗ này em chưa hiểu: ...") and ask — NEVER pretend to understand and guess a direction. This outranks everything else: if the goal is unclear, resolve it before the other questions matter.
1. **Spec-vs-code contradictions** — the task note may simply be WRONG (BA-AI-generated): spec says field/behavior X, code shows Y. Surface with evidence from both sides; never silently follow either side.
2. **Missing decisions** — defaults, scope boundaries, backwards-compat strategy, edge cases the spec ignores.
3. **Ambiguities** — wording that allows 2+ readings.

### Step 6: ONE batched question round

Present a single report, then ask **everything at once** — never dribble questions across turns:

```markdown
## 📋 Task: <title> (<Notion link>)

### Goal (trusted)
<1-3 lines>

### Claim verification
| Spec claim | Verdict | Evidence |
|---|---|---|

### Numbers gathered
- <metric>: <value> (source)

### ❓ Decisions needed (answer in one reply)
1. <contradiction/decision> — options A/B, my recommendation + why
2. ...
```

- ≤4 key decisions → use AskUserQuestion (multi-question, with recommended option first).
- More → numbered prose list, grouped by theme, each with a recommended default so the user can reply "1A, 2B, còn lại theo đề xuất".

Ask in chat and wait — the gate does not advance on silence.

### Step 7: Record & hand off

After answers:
- Write the agreed requirements into the session plan (and optionally post a summary comment back to the Notion task — ask once before posting).
- Proceed to `/plan-v2` (feature) or `/fix` (bug) with the verified requirements. Phase order for features: B1 admin setting → B2 backend API → B3 storefront/extension, one layer at a time.

## Rules

- **No coding, no file edits** during analysis — this skill is read-only investigation + questioning.
- Questions must be **honest about their type**: goal-confusion questions admit "em chưa hiểu X" and explain what's confusing; contradiction questions show evidence from both spec and code; decision questions name options + a recommendation. "Bạn muốn gì?" with no context is not a question this skill asks.
- If the spec is entirely consistent with code and has zero open decisions (rare), say so explicitly and skip the question round — don't invent questions.
- Always check backwards-compat for existing shops; if untouched by the spec, raise it as a decision, not an assumption.
