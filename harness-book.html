Harness handbook

Installing and running a development workflow where several specialised Claude sessions work one feature in parallel.

1. What problem it solves

One session doing a whole feature accumulates context as it goes: it reads the code, writes the code, then reviews the code it just wrote. By the end it is both slow and biased, and nobody is good at catching their own mistakes.

This harness splits a feature across several specialised sessions, each in its own terminal tab, all on one git worktree. They call each other, bounce work back and forth, and escalate to you at only three decision points.

RoleDoesReads the parent's findings?
scoutSurvey, verify against real code, write the plan. Stops at the plan gate.Yes
coderImplement the plan, one phase at a time.Yes
researchAnswer the coder's questions with file:line evidence.Yes
uxDesign the interface before the coder writes anything.Yes
reviewerRead the diff with unprimed eyes.No, deliberately
checkerJudge by running it, not by reading.No, deliberately
Why reviewer and checker are kept in the dark. Knowing the parent's conclusions destroys the one thing these two roles exist for. The reviewer is worth having because its eyes are unprimed; the checker is worth having because it demands evidence from a real run. Do not "make it consistent" with the other four.

2. Install

git clone https://github.com/MeanHoang/claude-harness ~/claude-harness
cd ~/claude-harness

./install.sh /path/to/project           # copy into the project (default)
./install.sh /path/to/project --link    # symlink instead, one shared source

The default is copy. This is a package you paste into a project, and each project is then free to diverge. Nothing at the destination is destroyed: a pre-existing real file is renamed to *.bak.<timestamp> first.

Use --link when you want a single source of truth. Editing a skill inside the project then edits it here, and one git commit in this repo captures it. The trade-off is that every project sharing the link changes together.

settings.json and settings.local.json are never written: they carry per-project permissions and hook wiring. Wire the hooks by hand after installing.

Fill in your own values

Project-specific values were stripped before publishing and replaced with {{VARS}}: package paths, cloud project ids, git remote, store domains, test identities. Fourteen in all.

cp harness.config.example harness.config     # fill it in; it is gitignored
./fill-vars.sh /path/to/project harness.config

fill-vars.sh is idempotent, and any {{VAR}} with no matching key is left visible and reported. Nothing is silently replaced with an empty string.

Requirements

  • git, because the harness is built on git worktree
  • cmux for workspaces and tabs. Without it the worktrees still work; you just open the sessions by hand.
  • python3, used by ship-board.sh and fill-vars.sh

Declaring what your project requires

bootstrap-worktree.sh checks that a fresh worktree has its guards. By default it requires readonly-intent-guard.sh, branch-guard.sh and settings.local.json. If your project needs more, list them in .claude/harness-required.txt, one path per line:

.claude/skills/<your-pipeline-skill>/SKILL.md
.claude/hooks/<your-hook>.sh

That keeps the shared script free of any one repo's skill names.

3. The life of a feature

  1. Open it. .claude/scripts/feature-open.sh <slug> [task-url] [feature|bugfix|chore|improve] does five things in one command: creates the worktree, equips it with the harness, creates progress.md, creates a cmux workspace, and opens six tabs named after the roles.
  2. Load the context. The script writes kickoff-scout.md with the research section blank. A child session is born with zero memory: whatever you do not write into that file is gone. Do the research in the parent session and fill it in, including the file:line you already found, which conventions apply, and which questions the child must put to the user rather than guess.
  3. Start the scout. See section 5; there are traps.
  4. Let it run. The scout writes a plan and stops at the gate. You approve. The coder works phase by phase, reviewer and ux bounce findings back, the checker runs it for real. Only three gates reach you: approve the plan, approve the code, settle a trade-off.
  5. Watch it. .claude/scripts/ship-board.sh prints every running feature, with whatever is waiting on you flagged 🚦 and sorted to the top.

4. Where the state lives

.claude/ship/<slug>/progress.md is the single source of truth for a feature. A machine-readable state block sits at the top; everything below it is for humans.

<!-- state
slug: <slug>
branch: bugfix/<slug>
kind: bug            # bug | feature
step: 3              # 0..7
phase: -
awaiting: user       # scout|coder|research|reviewer|ux|checker|user|none
round: 0             # coder-reviewer rounds; at 3 you must ask the user
gate: decision       # none|plan|code|decision  <- anything but "none" means WAITING ON THE USER
verdict: fix         # kind: bug only
-->
The state block drifts out of sync with the NOW line at the bottom. This has happened for real: state said awaiting: coder while NOW said "blocked, waiting for the user to decide". When they disagree, trust the NOW line. It gets updated by hand at the end of every turn; the state block is the one people forget. Fix the state block the moment you notice.

5. cmux traps, read before starting any role

Trap 1: cmux send types into the current command line and does not clear it.
Any tab holding unsubmitted text will mangle your command. Seen for real: a tab already held ! gcloud auth login, the launch command was appended to it, and the shell ran loginclaude --dangerously-skip-permissions …. gcloud swallowed the whole thing and the session never started. Always send ctrl+u first.
Trap 2: looking a role up by name with awk misses the selected tab.
The selected row is prefixed with *, so $2 is surface:13 rather than the role name. Strip the asterisk before splitting columns: 
sid=$(cmux list-pane-surfaces --workspace "$WS" | tr -d '*' | awk '$2=="scout"{print $1; exit}')
Get this wrong and the command falls through to whichever tab is selected, which may be a different role or a different feature entirely.
Trap 3: workspace and surface ids are renumbered every time a workspace is closed and reopened. Always look them up by name; never hardcode an id into a script or a kickoff file.
Trap 4: long strings containing $(cat …) often fail to send. The reliable route is a short one-line command pointing at a script file: 
printf 'cd %s\nexec claude --dangerously-skip-permissions "$(cat %s)"\n' "$WT" "$KICKOFF" > /tmp/launch.sh
cmux send --workspace "$WS" --surface "$SID" $'bash /tmp/launch.sh\n'
Note the trailing \n: cmux send does not press Enter for you.

Confirming a session actually started

There is no command to read a pane's contents, so check the process table instead:

for p in $(pgrep -f "bin/claude"); do
  lsof -a -p "$p" -d cwd -Fn 2>/dev/null | sed -n 's/^n//p'
done | grep <slug>

6. Why child sessions run --dangerously-skip-permissions

They run unattended. A command containing $(…) or a pipe cannot be analysed statically, so Claude Code always asks, and the session sits there waiting for a human to click Yes.

It is safe because hooks are not bypassed. Verified experimentally: running claude --dangerously-skip-permissions -p with a read-only prompt still had readonly-intent-guard deny the Write, and the file was never created. The flag drops the permission prompt, not the guard rails.

That is exactly why bootstrap-worktree.sh is mandatory. A worktree missing its hooks, running in bypass mode, is an agent under no rules at all.

7. The rules that keep quality up

Re-verify the parent; do not re-investigate

The four context-reading roles (scout, coder, research, ux) open their report with exactly this line:

Parent check: confirmed X/Y · refuted: <claim, why, file:line> · parent missed: <new finding>

A refutation belongs on that first line, never buried at the end: the parent is using that very conclusion to answer the user.

Calling another role means actually calling

Writing "handed this to the coder" in your own report makes nobody run. Seen for real: the reviewer wrote "still open: a UX question", the ux session wrote "waiting to be called", and the two waited on each other indefinitely until the user carried the message himself.

Before proposing any new field, helper, or component

  1. Does this value already exist somewhere? Grep the concept, read the type definitions, read the entire return value of the related service.
  2. Can it be derived from data you already have?
  3. If you genuinely must create it, which places did you already search? List them.

This failure is real: a session burned a whole day when the actual defect was only "the value already exists but is never passed up, so it lands in the wrong fallback branch", and the report went in circles before proposing a brand-new field.

8. For bugs, use bug-check rather than opening a feature

The output of bug-check is a diagnosis, not code. No branch, no worktree, no plan. One session, three legs, a report, then stop.

LegWhat to find
1. The problemThe exact symptom, whether it reproduces, how many places are affected
2. The codeWhich path it travels, with concrete file:line. Never infer from a function name.
3. The configurationThe actual settings on that environment. Most bugs live here.

Put the three together and look for the mismatch: the configuration says A while the code reads B, and that is the break.

Exactly one of four verdicts: fix, skip, need-data, need-logging. When you are not sure, need-data and need-logging are legitimate answers, not failures.

9. Describing a bug to someone who has never touched the flow

This block is mandatory at the top of every bug-fix plan. Exactly five lines, one sentence each, each carrying a real number:

LineContentExample
ObservedSymptom plus real numberslog shows Refunded $18 · Remaining $50
ExpectedThe correct number or behaviour18 + 50 should equal 60
SettingWhich setting field, on or off"reward additional fee" = OFF
Wrong fieldName, real value, sourcetransactionTotal=18 (gross) vs currentSubtotal=50 (net)
Break pointOne sentence plus file:linetwo numbers on one row, two different bases, x.js:1569

Plus a single Flow line, every hop carrying its file:line:

webhook X -> controller.js:1547 (writes) -> helper.js:12 (computes) -> render.js:148 (displays)
If you cannot fill a line, you do not understand the bug yet and may not write the plan. Write "line 3 unknown, need to read the settings", go and get it, and never pad a box to look complete.

Every warning in this handbook comes from something that actually went wrong, not from a hypothetical.
